Rule: new business logic goes in a service, routers stay thin. New Celery tasks go in the matching `tasks/` module.

Local tooling (A7-07): `worker/` (`relocate_tracks.py`) + `server/deezer/` (`extractor.py`, `sync_checker.py`) run on the PC where Rekordbox is installed — they read the local Rekordbox library, outside the server runtime. `worker/bpm_backfill/` (E2.b) is another local tool run on the PC in a Docker Linux container (Essentia doesn't install on Windows): it derives an estimated BPM from Deezer previews (`RhythmExtractor2013`, confidence-gated >=2.0) and writes `bpm_source='analysis'` to prod via the `ssh diggy-vps … psql` channel — dry-run by default, `--apply` to write, `bpm IS NULL` guard so a trusted bpm is never overwritten. **Since E2.c this local tool is an OPTIONAL manual accelerator** — the main mechanism is the nightly VPS Celery task `analyze_bpm_previews` (essentia+ffmpeg are now in the shared worker image; see Celery Beat Schedule). `worker/embedding_backfill/` (C9.a) is a third local Docker tool (essentia-tensorflow, Discogs-EffNet): `backfill_embeddings.py` computes the 1280-d audio embedding of Deezer previews and writes them to prod `track_embeddings` via the same `ssh diggy-vps … psql` channel (dry-run default, `--apply`, keyset `--after-id`, idempotent LEFT-JOIN `te.id IS NULL` + `ON CONFLICT DO NOTHING`); `eval_at_scale.py` re-runs the C9.0-bis neighbours-vs-co-occurrence eval at real scale (read-only, reuses `docs/c9-benchmark/embed_eval.py`). It is the PRIMARY backfill mechanism for the whole C9.a horizon (a VPS fil-de-l'eau task is deliberately DEFERRED — EffNet ≈ 8 CPU-s/track, too heavy for the fair-use VPS at the current ~4.5k/day inflow; see the C9 memory). `worker/import_rekordbox.py` is archived in `docs/completed/` (the official import flow is the web XML upload via the `import_rb` router). `scripts/local/trackid_spider/` (C11) is a repo-root LOCAL tool (stdlib + httpx, no server package, no prod connection): it spiders the TrackID.net `/audiostreams` listing (STRICT 1 req/s, static `addedOn` window plan, resumable per-window checkpoints) into a local SQLite staging (raw mirror) and exports NDJSON/CSV on the `trackid_index` column contract, which the OPS script `server/api/scripts/import_trackid_index.py` imports into prod. A `probe` mode runs the A.0/V1-V6 validations (windowing, `pageSize` cap = 100, `rowCount` free pre-scan) and produces the completeness/volumetry reports. `worker/beatport_backfill/` (2026-09) is a fourth local Docker tool: it drains the Beatport enrichment backlog from the operator's RESIDENTIAL IP in parallel with the VPS hourly drain to halve the catch-up time. The lever is per-IP rate limiting, NOT compute — Beatport 429-rate-limits **per source IP** (the VPS cap can't just be raised without banning the datacenter IP), so a 2nd residential IP = a 2nd independent ~rps quota (the probe proved 6 rps sustained with 0×403). It ONLY scrapes+validates inside the PROD server image (reuses `workers.enrichment._search_beatport_async` VERBATIM — the X3/X4 matchers, zero re-implementation) and emits an NDJSON of matches; the WRITE is done on the VPS by the OPS script `server/api/scripts/import_beatport_matches.py`, which reuses `beatport.enrich.enrich_from_beatport` + `workers.enrichment._mark_searched` VERBATIM (so provenance, artwork upload AND merge-on-collision are the drain's real code — invariant #4). PULL = fresh Tier-1 only (`beatport_id IS NULL AND beatport_searched_at IS NULL`, ordered by the C12 `enrich_priority` scalar); the E1 30/90-day retries stay 100% the VPS's job. Dry-run by default (read-only end-to-end — the OPS script rolls back AND suppresses the MinIO/CDN artwork upload in dry-run), `--apply` writes (DUMP PROD FIRST). Scrape rate is env-tunable via `BEATPORT_RATE`/`BEATPORT_CONCURRENCY` in `workers/rate_limiter.py` (defaults `0.66`/`2` = **PROD UNCHANGED** unless the env is set; only the local container sets it higher — the shared Redis window stays 0.66 and fails open locally so the bucket governs). Run it in the VPS Beatport off-hours (~23h→6h) to avoid overlap; `--shard M/N` (`id % N`) enables concurrent disjoint salvos. `worker/trackid_hydrate/` (2026-09) is a fifth local Docker tool — the **clean-hydration** pipeline for TrackID sets (LOCAL compute, VPS commit, per batch of N sets): `hydrate.py` (host, stdlib) pulls a `not_hydrated`+scored worklist from `trackid_index` (ssh-psql), fetches each set's TrackID detail (reusing the C12 `scripts/local/trackid_spider/shadow.py` adaptive-rate fetch + prod-faithful `merge_tracklist`/`is_id_track`), runs the container driver `enrich_driver.py` (`FROM ${SERVER_IMAGE}` + EffNet — reuses `workers.enrichment._search_deezer_async`/`_search_beatport_async` VERBATIM, shares ONE Deezer preview download across Essentia BPM + EffNet embedding run off the event-loop on a ThreadPoolExecutor), and assembles a per-set **bundle** NDJSON (set `detail` + per-track {Deezer `/track` hit, Beatport match, gated BPM, 1280-d embedding, cover bytes} + top-level `set_artwork_b64` bytes). Dry-run default; `--apply` pipes the bundle to the OPS script `--apply` (DUMP PROD FIRST). **The local tool and the VPS drain run IN PARALLEL without conflict via a dynamic CLAIM/LEASE (migration 0055, `trackid_index.claimed_at`), NOT a static shard** (a first static-shard approach `TRACKID_BACKFILL_EXCLUDE_SHARD`/`--shard` was superseded and removed — it froze a fixed half of the backlog): in `--apply` the local ATOMICALLY reserves its batch — a data-modifying CTE flips the top-N `not_hydrated` scored rows to `hydration_state='claimed'` (+`claimed_at=now()`) under `FOR UPDATE SKIP LOCKED`, so the VPS drain (which selects only `not_hydrated`) skips them; on push they flip `claimed→hydrated`, and a `finally` releases any un-pushed claim back to `not_hydrated`. The VPS drain REAPS stale claims (`claimed` older than `TRACKID_CLAIM_LEASE_SECONDS`, default 7200) back to `not_hydrated` at the start of each run → self-heals a hard local crash (a batch running longer than the lease can be reaped mid-flight → a harmless idempotent double-hydration, so keep `--limit` modest or the lease high). Dry-run / `--dry-run-push` stay READ-ONLY (no claim). So stopping the VPS drain is NO LONGER needed. Cadence knobs `DEEZER_RATE` (1.0 default, C9 residential-IP lesson) / `BEATPORT_RATE` / `HYDRATE_EXECUTOR_WORKERS`; the local image adds `essentia-tensorflow` (cp313 wheel, TF ~500 MB) atop the python-3.13 server image. Throughput is EffNet-bound (~8 CPU-s/track) → a multi-week marathon over the C12 scope (~297k sets).

## Database

`catalog` is the ONLY hub. Everything points to it via `catalog_id`.

- Dedup via `normalized_key` (artist|title) or `isrc` at ingestion. Since X1 (2026-07-22) enrichment also folds a row into a pre-existing one **only when it is the same recording** — guard `workers/catalog_merge.same_track` (equal ISRC, else remix-aware `normalize_track_title`); the FK-safe merge primitive `merge_catalog_entries` (+ `pick_canonical`) is wired at the enrichment write points by `workers/catalog_dedup.py`. **Platform ids (`deezer_id`/`beatport_id`) are NOT a per-recording identity** — pre-X3, Deezer search stamped `hits[0]` unchecked (a remix inherited the original's deezer_id) and the Beatport release fallback shared one beatport_id across an EP; ~77%/94% of those id-groups are DISTINCT recordings. So NEVER dedup/cluster on a platform id alone, and there is deliberately **no unique index** on them. Since X3 (2026-07-22) enrichment VALIDATES the match before stamping an id: Deezer hits are checked against the entry (`deezer_enrich._deezer_hit_matches` — equal ISRC, else remix-aware `normalize_track_title` + folded artist) and the Beatport release fallback requires a remix-aware title match (`beatport/client._release_title_matches`); the gate lives in BOTH the sync and async twins of each searcher, and a non-match stamps nothing so the row stays E1-eligible (better no id than a wrong id). ## Data Authority Principles

These are project invariants. Never propose code that violates them.

1. **Rekordbox is read-only** from Diggy's perspective — for the SERVER runtime. All server write operations stay within Rekordbox itself. **Accepted exception**: the LOCAL tool `worker/relocate_tracks.py` (run on the DJ's own PC, outside the server, via `pyrekordbox.Rekordbox6Database`) DOES write back to the Rekordbox library (`db.session.commit()`) — it is a local Rekordbox-side utility, not part of the Diggy server, so it does not breach the invariant for the app.
2. **Rekordbox BPM is authoritative** over all external sources for the user's performance data.
3. **Beatport is the canonical authority** for BPM and key in the shared catalog (`bpm_source` / `key_source` track provenance). Since E2.b, `bpm_source='analysis'` is a **lower-authority** estimated BPM derived from Deezer preview audio (Essentia `RhythmExtractor2013`, confidence-gated ≥2.0) — written only where `bpm IS NULL`, never over a beatport/rekordbox value, and overwritten by a later Beatport enrichment. It DOES feed `similarity_service` (bpm is a scoring feature, accepted). No `analysis` key is ever written (E2.a benchmark: NO-GO on key).
4. **Merge asymmetry**: duplicate rows (false negatives) are cheap storage debt; bad merges (false positives) are expensive data corruption. Always err toward separation.
5. **LLMs handle language-boundary tasks only** (normalization, classification assistance, explanation, extraction). They never compute similarity scores and never write directly to DB.

## Auth & Multi-User

- Auth: Google OAuth ONLY. There is no email/password login. OAuth `state` is validated server-side via Redis (`oauth_state:{state}`, TTL 5min, one-shot delete). No localStorage.
- Token delivery: temporary `auth_callback` cookie (base64url no padding, 60s TTL, Secure, SameSite=Lax, httponly=False). Backend 302s to `/login/callback`, frontend reads then deletes the cookie.
- This cookie flow exists because of Safari iOS: hash fragments are dropped on 302 redirects, CSP `script-src 'self'` blocks inline scripts, sessionStorage is lost on cross-origin navigation. Do not "simplify" it back to fragments or storage.
- `uid()` returns `None` for guests. There is no `user_id=1` fallback anymore. Every user-conditional query must handle `None`.
- Catalog read visibility (C3): every query returning `catalog` rows to a reader MUST apply `catalog_service.catalog_visible(user_id)` (ORM predicate) or `catalog_visible_sql(user_id[, alias])` (raw `text()` fragment — bind `:viewer_id` ONLY when `user_id is not None`; the same bind is reused by the `user_track` EXISTS, no extra param). Guests see `scope='shared'` only; an authenticated user sees `shared` rows, their own `owner_id` private rows, **plus any row they hold a `user_track` for** (their imported library). A foreign private row therefore stays hidden UNLESS the viewer imported that same track. Guests keep browsing (no login wall — deliberate: discovery stays open). This third `user_track` clause is what un-blinds a Rekordbox importer: RB import dedups on the globally-UNIQUE `normalized_key`, so a user importing a track that collides with another user's private row is bound (via `user_track`) to that existing row and sees it through this clause — the foreign row is NEVER promoted or mutated. Do NOT "fix" the collision by flipping the foreign private row to `shared`/`owner_id=NULL` (a rejected design: it leaks the owner's private track to guests and every user — a name collision is not a platform match). NOT filtered (accepted residual, non-identifying or disproportionate): aggregate-only counts (genre stats, artist `nb_catalog`) and set tracklists (ORM `set_track.catalog` traversal). Any new catalog read path must add the predicate.
- `/storage/*` artworks are served unauthenticated by nginx (proxied MinIO), IDs sequentially enumerable — a deliberate C3 deferral: cover images only, enumeration reveals existence, not private data. `<img :src>` cannot carry a Bearer header, so protecting them needs a cookie `auth_request` or signed MinIO URLs (future work).
- Admin: `is_admin` flag + `require_admin` dependency. Destructive admin actions are logged in `admin_audit_log`.
- Admin/ops endpoints with no UI (curl only): `POST /api/watchlist/` (register a new source playlist by URL — `GET /api/watchlist/` itself backs WatchlistView and is not admin-only). Since D10 the formerly curl-only `POST /api/admin/reset-beatport` (Enrichissement tab, inline confirmation guard), `POST /api/admin/artists/backfill-multi-artists` (Enrichissement tab) and `POST /api/admin/sets/{id}/detach` (Sets tab — « Sets attachés » section) ARE exposed in the admin UI.

**Command hygiene (Claude — avoid needless permission prompts):** the Bash tool's cwd **persists** across calls, so `cd` into a subdir in its OWN call — never `cd server/frontend && npx vitest …` inline. The inline `cd X && cmd` form makes the whole command start with `cd`, which no longer matches the command's allow-list prefix (`Bash(npx vitest:*)`, `Bash(ruff check:*)`, …) and forces a prompt. Frontend commands (`npx vitest run`, `npm run lint`) run from `server/frontend`; backend (`pytest`, `ruff check server/`, `alembic`) from the repo root. Same idea for the VPS: use `ssh diggy-vps "…"`, not the raw `-i` key form. To kill a Windows PID from this shell, use PowerShell `Stop-Process -Id N -Force`, not Bash `taskkill //PID N` (Git Bash mangles the `//` flags → « Argument ou option non valide - //PID »).

Env vars: see `.env.example` at repo root. Required: `POSTGRES_USER/PASSWORD/DB`, `DATABASE_URL`, `JWT_SECRET`, `MINIO_USER/PASSWORD`. Prod adds `COMPOSE_FILE=docker-compose.yml:docker-compose.ssl.yml` and `DOMAIN`. `ENV=production` disables permissive CORS and the API docs (`/api/docs`, `/api/redoc`, `/api/openapi.json` are not registered).

## Known Pitfalls

### Nginx
- `add_header` in a `location` block REMOVES all server-level headers. Asset locations must be nested inside `location /` without their own `add_header` to inherit the CSP.
- `/api/`, `/storage/`, `/minio/` use `^~` prefix priority so they are not captured by the assets regex `\.(js|css|jpg)$`.
- The active prod config is `default.ssl.conf.template`. `default.conf` is intentionally empty.
- Keep CSP `upgrade-insecure-requests` as long as any `http://` request can arrive.
- `client_max_body_size` (12M) is coupled to the Rekordbox XML import limit (`MAX_FILE_SIZE` 10MB in `import_rb.py`): keep nginx slightly above the app limit so the app returns its French 413 message, and raise both together.

### Docker & Backup
- api/worker/worker_enrich/beat share ONE image built from context `./server` (`server/Dockerfile` copies `api/` + `workers/`). Prod runs the code baked into the image — hot reload only exists through the local override bind mounts.
- The `postgres` service is now a **custom-built image** (`postgres/Dockerfile` = `postgres:16-alpine` + pgvector v0.8.0 from source, `with_llvm=no` + `OPTFLAGS=""`), tagged `diggy-postgres:16-pgvector` (C9.a). `docker compose build` rebuilds it; a deploy that ships a postgres image change needs the container recreated (see the pgvector deploy gotcha in Deploy). CI runs its tests against `pgvector/pgvector:pg16` (the `vector` extension must exist for `create_all` to emit `vector(1280)`; `tests/api/conftest.py` runs `CREATE EXTENSION IF NOT EXISTS vector` on the PG path).
- `server/.dockerignore` excludes `frontend/`, `nginx/`, `scripts/`, `deezer/` from the build context: a new directory under `server/` needed at runtime must be removed from that file, or it silently won't ship.
- The `backup` service mounts `/root/.config/rclone` read-write (VPS-only path): rclone rewrites its OAuth token on refresh — never make this mount `:ro`. Offsite = encrypted PG dumps only (MinIO mirror stays local by design).

### Hébergement & ressources VPS (Hostinger)
- Le VPS = **4 vCPU** sous police **fair-use CPU** (moyenne soutenue) ; RAM 15 GiB et disque sont larges (jamais le facteur limitant à ce jour). Le graphe CPU du panel Hostinger montre l'**usage réel** (% des 4 vCPU), PAS un plafond imposé — un throttle appliqué se lit en `%steal`, pas comme un palier plat.
- Diagnostic ressources : **`ssh diggy-vps` + `docker stats --no-stream`** (temps réel par conteneur) et **`sar`** (sysstat installé, historique ~10 j CPU/mém/réseau dans `/var/log/sysstat/saNN`, granularité 10 min, split user/system/iowait/steal). Limite : `sar` ne garde PAS la conso **par process** dans le passé (accounting pidstat off), et il n'y a ni netdata ni prometheus.
- **Piège OPS majeur (throttle 2026-08-19, chantier AV10)** : un rollout OPS qui rend un GROS lot de lignes ré-éligibles à l'enrichissement (ex. X4 `reverify --pre-x3` = ~180k ids reset le 12/08) déclenche **~6-7 jours de CPU soutenu ~80 %** — non par un pic de débit (les drains restent plafonnés, item-count CONSTANT) mais par le **travail par item qui passe de skip rapide à ré-enrichissement réel + churn d'UPDATE sur `catalog` → autovacuum quasi continu** (profil `sar` : `%user`≈`%system`, réseau/mémoire/iowait PLATS). Ça peut tripper le fair-use. Avant un gros reset, prévoir d'**étaler le re-drain** (baisser le cap `/jour` le temps de la résorption). Ce n'était PAS la tâche BPM (constante avant/après le pic).
- **Plafonner le pic CPU BPM** : `analyze_bpm_previews` tourne un `ThreadPoolExecutor(max_workers=ANALYSIS_BPM_EXECUTOR_WORKERS)` (défaut **2** → 2 cœurs Essentia épinglés 00h→03h). Posé à **1** dans le `.env` VPS (var lue à l'import du worker → `docker compose up -d worker_enrich` pour appliquer, PAS de deploy de code). Hygiène CPU « gratuite » côté compose : workers/beat `--loglevel=warning` (moins de logs à démuxer par dockerd, qui pesait 23 %) + healthchecks postgres/redis/minio à 60s (pas 10s).

### Workers & Celery
- Every long-running task holds a Redis lock: atomic `SET NX EX`, TTL strictly above the task's `time_limit`, release conditional on still owning the lock (reference pattern: `tasks/catalog.py`). Never check-then-set, never a TTL below the time_limit. Depuis AV4 c'est vrai de TOUTES les tâches longues (`lock:enrich_deezer`, `lock:crawl_trackid_latest`, `lock:sync_artists`, `lock:link_set_artists`, `lock:backfill_multi_artists`, + le lock ORCHESTRATEUR `lock:reclassify_genres` acquis par `reclassify_all_genres` et relâché par le callback/errback du chord — jamais sur `reclassify_genres_chunk`, dont le fan-out parallèle doit rester non-lock).
- **Jamais `autoretry_for=(Exception,)` sur une tâche à soft-limit** : `SoftTimeLimitExceeded` EST une `Exception`, donc le décorateur transforme un timeout en boucle de retry (a mordu 2026-07-13 backlog artistes, 2026-08-10 reclassify OOM). Depuis AV4 aucune tâche de `workers/tasks/` ne porte plus cet autoretry : le broker (`task_acks_late` + `task_reject_on_worker_lost`) re-livre un crash une fois, et le lock + le budget/soft-limit-catch bornent le run. Un retry n'est légitime que TYPÉ (tuple d'exceptions ciblées excluant `SoftTimeLimitExceeded`/`Retry`) sur une tâche courte idempotente.
- **Le catch `SoftTimeLimitExceeded` ne suffit PAS sur un drain asyncio** : le signal billiard peut être levé PENDANT un write des internals asyncio et avalé par le handler d'erreur du transport (« Fatal write error on socket transport », prouvé Sentry DIGGY-APP-J) → il n'atteint jamais le `except` de la tâche, le run court jusqu'au hard limit puis SIGKILL (travail non commité perdu + lock orphelin ≤TTL). Depuis AV9 (2026-08-17), les 5 drains (`enrich_catalog_beatport`, `enrich_catalog` Deezer, `analyze_bpm_previews`, `backfill_trackid_sets` [ajouté 2026-08-24 pour DIGGY-APP-4 : garde en tête de SES DEUX boucles imbriquées collecte+import], + `backfill_multi_artists` [ajouté 2026-09-03/AV11 pour DIGGY-APP-T/V/W : hard limit 9000s → SIGKILL]) DOUBLENT le catch d'une deadline interne `time.monotonic()` = soft limit − `DEADLINE_MARGIN` (120s, env `ENRICH_DEADLINE_MARGIN` / `ANALYSIS_BPM_DEADLINE_MARGIN` / `TRACKID_BACKFILL_DEADLINE_MARGIN`) vérifiée en TÊTE de chaque batch → `break` propre (flush partiel déjà commité, stats, retour succès, release lock au `finally`), stat additive `deadline_hit` dans `crawl_logs`, rien stampé sur les entrées non atteintes (invariant E1). Les soft limits sont des constantes module (`DEEZER_SOFT_TIME_LIMIT`/`BEATPORT_SOFT_TIME_LIMIT`/`ANALYSIS_BPM_SOFT_TIME_LIMIT`/`TRACKID_BACKFILL_SOFT_TIME_LIMIT`/`BACKFILL_MULTI_ARTISTS_SOFT_TIME_LIMIT`) partagées décorateur+garde — ne jamais lire `task.soft_time_limit` à l'exécution. Toute NOUVELLE tâche à drain long par batches sur asyncio doit porter la même garde (le catch signal reste en défense en profondeur).
- Une panne HTTP externe n'est PAS une tentative de recherche : `DeezerHTTPError`/`BeatportHTTPError` (levées sur non-200 dans `workers/async_http.py` + `workers/enrichment.py`) sont catchées en `errors+=1` SANS `_mark_searched`, pour que l'entrée reste éligible au re-scan E1 (un outage ne doit pas brûler une des 3 tentatives). Même esprit dans `enrich_deezer_batch._enrich_one` : la PK est résolue EN TÊTE (`entry_id`) sous garde, et `ObjectDeletedError` (ligne supprimée mid-batch par un merge concurrent) est attrapée → `errors+=1` SANS `_mark_searched` ; la garde + un handler dédié empêchent qu'une race par entrée remonte hors du `asyncio.gather` et fasse échouer toute la tâche (DIGGY-APP-10). Depuis AV11 (2026-09-03) la fonction PARTAGÉE `_load_m2m_artist_names` (Deezer ET Beatport) garde AUSSI son `[e.id for e in entries]` sous `except ObjectDeletedError` (skip la row morte) : elle tourne AVANT le try par-entrée, donc une entrée supprimée mid-batch par un merge concurrent y levait `ObjectDeletedError` et tuait tout le batch Beatport → DLQ (DIGGY-APP-1E/4).
- Deezer/Beatport rate limits are shared across worker processes via a Redis fixed window inside `rate_limiter.py` (fail-open to the local bucket if Redis is down). Instantiating `RateLimiter()` per task is fine — the global cap holds anyway.
- Destructive cleanup of a watched playlist triggers ONLY on `PlaylistGoneError` (typed per source in `source_clients.py`), never on string-matching an exception message. Sa jumelle `DeezerQuotaError` (`source_clients.py`, codes Deezer 4/700) est un signal de quota/rate-limit TRANSITOIRE, PAS un déclencheur de cleanup : `crawl_single_playlist` l'attrape au niveau du WRAPPER (couvre `fetch_meta` ET `fetch_tracks`, qui passent tous deux par `_deezer_get`) et renvoie un skip gracieux (`reason="deezer_quota"`) — pas de DLQ, pas de log ERROR, re-dispatché au prochain beat `crawl_radar` (un quota externe n'est pas un échec terminal, DIGGY-APP-4).
- Never `result.get()` inside a task (blocks a worker slot for the whole run) — use a `chord` with a finalize callback + errback (pattern: `tasks/genres.py`).
- A cadence gate compared against a daily beat needs slack: the beat fires every 24h sharp but the reference timestamp is stamped DURING the previous run, so a strict `elapsed > 1d` check skips every other run (daily tier → every other day). Subtract `CADENCE_SLACK_DAYS` (0.25) from the threshold — pattern: `tasks/radar.py` + `tasks/sets.py`.
- Un déploiement (`docker compose up -d`) qui recrée les workers **pendant** un run enrich tue le process (SIGKILL) sans exécuter la release conditionnelle du lock → `lock:enrich_beatport` orphelin qui fait skip la tâche suivante jusqu'à expiration du TTL (MON, constaté 2026-07-22). Mitigé par le TTL court (3900s depuis le drain horaire) : au pire 1 créneau sauté. Remédiation à chaud : `redis-cli DEL lock:enrich_beatport` **seulement si** `celery … inspect active` ne montre aucune tâche. Éviter de pousser sur master pendant les fenêtres enrich (Beatport 6h→23h, Deezer 05:00). Depuis AV4 le même risque d'orphelin (et la même remédiation `redis-cli DEL lock:<clé>` sous la même garde « aucune tâche active ») vaut pour tous les nouveaux locks courts : `lock:enrich_deezer` (Deezer 05:00), `lock:crawl_trackid_latest` (03:30), et les tâches artistes/genres admin/manuelles.

### Database & Alembic
- Since AU3 the API never runs `create_all`: the schema comes from Alembic ONLY (test harnesses keep their own `create_all` in `tests/*/conftest.py`). In local dev, the compose override runs `alembic upgrade head` before uvicorn.
- **CI runs pytest under xdist** (`-n auto --dist loadscope`, since bf141ed / 2026-07-24): every backend test must be **parallel-safe**. `tests/api` gives each xdist worker its OWN PostgreSQL database (`diggy_test_gwN`, created at session start via an autocommit maintenance connection under a shared advisory lock; `DATABASE_URL` is rewritten per worker BEFORE the app imports so every engine is isolated). Never reintroduce shared-DB serial assumptions (a per-test `TRUNCATE` on one shared DB corrupts sibling workers) or module-global mutable state. Keep `tests/api` self-sufficient re: Redis — it ships its own in-memory rate-limit stand-in; do NOT rely on another module's `sys.modules` redis mock (before the fix, `pytest tests/api` alone took ~5 min on slowapi's absent-Redis timeouts, "saved" only in the full run by `tests/worker/test_rate_limiter.py`). The SQLite path (default, per-process `:memory:`) is naturally isolated. A **PG-only worker test** (e.g. an `ON CONFLICT` upsert that SQLite can't run — `skipif` non-PG) must create its OWN throwaway database (mirror `tests/api`'s `_create_worker_database` maintenance-connection pattern), NOT `create_all`/`drop_all` on `DATABASE_URL`: under loadscope a worker process can run that module alongside `tests/api`, whose per-worker schema is session-scoped, so a `drop_all` on the shared URL would wipe it mid-run (`tests/worker/test_import_rb_upsert.py`, AV7).
- The migration chain is NOT replayable from an empty database: 0001 assumes the pre-Alembic tables historically created by `create_all`. A fresh local PG volume must be seeded from a prod dump (`docs/restore.md`); an old dev volume created by `create_all` must be stamped once (`alembic stamp head`). A baseline/squash migration is a known follow-up.
- `uq_artists_deezer_id` (partial unique on `artists.deezer_id`, sentinel-aware) is now declared at the model (`Artist.__table_args__`, with `sqlite_where` so the test harness reproduces it) and **shipped by migration `0034_uq_artists_deezer_id`** (`CREATE UNIQUE INDEX IF NOT EXISTS`, a no-op against the identical prod index — it was historically created by hand directly in prod, AU3 follow-up). See the MANUAL block of `docs/database-schema.md` before touching artist deezer_id uniqueness.
- NEVER `asyncio.gather` several `db.execute` on the SAME `AsyncSession`: a session is not safe for concurrent access. SQLite masks it, but asyncpg (PostgreSQL/CI) wedges a connection ("non-checked-in connection … will be terminated") and the suite HANGS. Await DB loaders sequentially on one session; if you truly need parallel DB reads, use separate sessions/connections. Bit us in C4 (`load_similarity_context`, `get_connections` — both since serialized).
- **`SAEnum(SomePyEnum)` persists the member NAME, not its value.** So a str-enum column round-trips against the migration ONLY if `name == value` for every member (the repo convention: `SetFlagType.duplicate_candidate = "duplicate_candidate"`, `AlbumType.album = "album"`). Bit C7-L1: `AlbumType.ALBUM = "album"` (uppercase name) emitted DDL labels `['ALBUM',…]` while migration 0046 created the PG type with `['album',…]` → prod INSERT would reject `"ALBUM"` and `alembic autogenerate` diffs non-empty. The test suite (SQLite `create_all` off the model) does NOT catch it — it never runs the migration, so it's self-consistent yet prod-broken. Keep enum members lowercase name==value, or pass `values_callable=lambda e: [m.value for m in e]` to BOTH model and migration.
- `StringArray` (custom `TypeDecorator`, `catalog.genres`) needs an explicit `comparator_factory` for `.any()`/`.in_()`: the base `TypeDecorator.Comparator` does NOT inherit `ARRAY`'s membership ops, so `genres.any(x)` raised `AttributeError` at query-build (a 500, latent since no code path exercised it until the Explorer genre filter). The fix (`models/base.py`) is a per-dialect-compiled `array_any` (`= ANY(col)` on PG, correlated `EXISTS json_each` on SQLite); its sibling `array_is_empty` (`coalesce(array_length(col,1),0)=0` on PG, `coalesce(json_array_length(col),0)=0` on SQLite; added for the admin genre-only enrich filter, AV1) follows the same shape — any new membership/predicate op on a custom array type must compile on BOTH dialects (SQLite backs the test suite).

### Frontend
- Container queries everywhere; `@media` ONLY for `position: fixed` elements.
- Zero hardcoded colors: everything via `var(--...)` from `diggy-tokens.css`.
- No multi-statement inline handlers in templates (`@click="a = 1; b = 2"`): Prettier reformats them across lines, which breaks the Vue compiler. Extract to a method.
- Responsive tables: columns hidden progressively (ExplorerView: 4 container-query paliers 1000/860/700/640). At <640px only Play / Track / BPM / Avis remain (Key drops before BPM — DJs favor BPM on mobile), play & avis always visible (touch).
- BottomNav (mobile <640px): 6 items + conditional Admin (Radar added D6 → 7 with Admin, tight on ≤360px); PlayerBar repositions above it.
- Celery task polling goes through `composables/useTaskPoll.js` (keyed timers, onUnmounted cleanup built in). Two sanctioned paginated-fetch patterns, NEVER a hand-rolled offset/hasMore fetch in a view: card grids with an IntersectionObserver sentinel → `usePaginatedList.js`; virtualised tables (windowing, no sentinel, page-built repeated params) → `useWindowedList.js` paired with `useVirtualWindow.js` (Explorer/D6, reused by Radar). Never reintroduce an ad-hoc `setInterval` poll either.
- The `.state` empty/loading message and `@keyframes spin` are global utilities in `assets/page.css`; views only keep scoped overrides for real divergences (mono, centered, fs-sm...). Don't redeclare the full block locally.
- Vitest: when `vue-router` is mocked, `stubs: { RouterLink: true }` is a no-op (VTU ignores string-name stubs for unresolved components) — register `RouterLinkStub` via `global.components` (pattern: BottomNav.test.js, LoginCallbackView.test.js).
- Scoped CSS + slots: content passed into a child via a slot keeps the PARENT's `data-v` scope id, NOT the child's — so the child component's scoped rules cannot target slotted content (and vice-versa). The child's `<slot>` cells ARE real grid children (no wrapper), so they occupy the grid tracks fine, but any styling of them (states like `.disliked` dimming, active-column band) must be re-declared in the PARENT's scoped block, e.g. `.tt-row.disliked > .rd-cell--score` in RadarView (matches because `.tt-row` is unscoped in that selector and the `.rd-cell--score` carries RadarView's `data-v`). Bit AV5 A4-01: `<TrackTable>`'s `.tt-row.disliked > .tt-cell` did NOT dim Radar's slotted score cells. Vitest can't catch it — verify RENDER.
- Grid `1fr` means `minmax(auto, 1fr)`: tracks can NOT shrink below their content's min-content (an `<img>` at natural aspect wins over the fr distribution). For image mosaics constrained to a fixed box, use `minmax(0, 1fr)` + `overflow: hidden` on the box. Corollary: positioned elements paint ABOVE later in-flow siblings — overflowing absolute content silently covers them (Artist Detail hero, 2026-07-20: a complete, correctly-styled DOM was invisible under the overflowing tiles). Neither vitest (no layout) nor static CSS reading catches this — verify RENDERING (headless screenshot) after any layout-sensitive change.
- **KeepAlive des vues listes (D9, 2026-08-17)** : les 6 vues listes (Explorer/Radar/Artists/Sets/Watchlist[=/playlists]/Genres) sont cachées par `<KeepAlive :include>` dans `App.vue` (allowlist des `defineOptions({ name })` de chaque vue, `:max=6`). **Les vues détail ne sont JAMAIS dans l'allowlist** (elles varient par param de route). Conséquences pour toute nouvelle vue liste OU tout watcher/effet dans une vue cachée : sous KeepAlive la vue reste **montée** en arrière-plan quand on ouvre un détail (`onUnmounted` ne fire plus au départ, seulement `onDeactivated`/`onActivated`). Donc (a) tout watcher `route.query`→state doit être gardé `if (route.path !== ownPath) return` (`ownPath` capturé au setup), sinon la query vide du détail clobbe les filtres cachés + déclenche un refetch fantôme (cf. `useUrlSync`/`useFilterState`) ; (b) les listeners globaux scroll/resize (`useVirtualWindow`) et les polls (`useTaskPoll`, ex. crawl WatchlistView) doivent se **détacher `onDeactivated` / se ré-attacher `onActivated`** ; (c) le scroll se restaure au retour via `useScrollRestore.reapply()` en `onActivated` (0 refetch, items en mémoire ; skip la 1ʳᵉ activation qui suit `onMounted`), PAS via le `restore()` du montage qui ne re-tourne plus. Vitest ne valide QUE l'allowlist + les noms — le comportement (retour instantané, 0 refetch, scroll conservé) se vérifie au RENDU headless.
- **Prefetch de nav (D9)** : `router.js` expose `prefetchRoute(path)` (fabrique `utils/prefetch.js` : map `path→loader` dérivée des routes lazy, dédup via Set, catch silencieux). SidebarNav/BottomNav l'appellent sur `@mouseenter`/`@focus` — précharge le **chunk JS** de la route visée (jamais de données, jamais au montage → aucune salve OOM sur `/api/radar/feed`). NB : les items Sidebar sont des `<span>` non focusables → le `@focus` clavier n'y est effectif que sur les `<button>` de BottomNav (limitation a11y pré-existante).
- **Toolchain front & plancher Node (N4, 2026-08-18)** : le front tourne sur vite 8 (bundler **Rolldown** — `vite build` découpe le socle en `index-*.js` ~119 kB + un chunk préchargé `_plugin-vue_export-helper-*.js` ~71 kB ≈ 190 kB, iso AV5 ; ce re-découpage est normal, pas une régression de poids), vitest 4, pinia 4, vue-router 5. **vue-router 5 a pivoté d'archi** : il tire ~18 deps runtime (unplugin/chokidar/`@babel/generator@8`…) là où v4 n'avait que `@vue/devtools-api` — toutes tree-shakées du bundle navigateur (0 fuite vérifiée), mais `@babel/generator@8` impose un **engine `node ^22.18.0 || >=24.11.0`**. Satisfait aujourd'hui par `node:22-alpine` (Dockerfile) et `setup-node "22"` (CI), qui résolvent la dernière 22.x flottante > 22.18 ; **ne JAMAIS épingler un tag `node:22.x` < 22.18** (EBADENGINE — non bloquant sans `.npmrc engine-strict`, absent, mais à éviter). ## Deploy

- Domain: `diggy-music.fr`. VPS project path: `/root/diggy`. `.env` lives ONLY on the VPS, never in git.
- Push to `master` → GitHub Actions (ruff + eslint + pytest on real PG + vitest + pip-audit) → SSH → `docker compose build` → `alembic upgrade head` (on the NEW image, before the switch) → `docker compose up -d`. A failing lint or pip-audit blocks everything (since AV2, pip-audit is a BLOCKING gate — `audit` is in the deploy job's `needs:`, `continue-on-error` removed; only advisories with NO upstream fix are explicitly `--ignore-vuln`'d, currently PYSEC-2025-185 jose + PYSEC-2026-1325 ecdsa); a failing build or migration aborts the deploy (old code keeps serving).
- **⚠️ First C9.a deploy (pgvector) — ordering gotcha**: `alembic upgrade head` runs against the CURRENTLY RUNNING postgres, BEFORE `up -d` recreates it. Migration 0049 does `CREATE EXTENSION vector`, which needs the NEW postgres image (`postgres/Dockerfile`, alpine + pgvector). So on the first deploy that ships this, recreate postgres FIRST — `docker compose up -d --build --no-deps postgres` — THEN let the migration run (or run it manually after). Same volume/major (PG16, musl→musl), no reindex. One-time; subsequent deploys are normal.
- SSH from Claude: **prefer the alias `ssh diggy-vps "…"`** — it matches the skill/allow-list rules (`Bash(ssh diggy-vps:*)`) so it won't prompt; the explicit form `ssh -i /c/Users/willi/.ssh/claude_diggy root@82.29.168.247` also works (dedicated key) but is more verbose.
- Prod read-only SQL (VPS): `ssh diggy-vps "cd /root/diggy && docker compose exec -T postgres sh -c 'psql -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\" -c \"SELECT …\"'"`. Gotchas: the DB service is **`postgres`** (not `db`); env vars must expand **inside** the container → wrap the psql call in `sh -c '…'`; table names are the SQLAlchemy `__tablename__` (e.g. `sets`, `set_tracks`, `catalog_artists` — NOT `dj_sets`).
- **OPS data scripts** live in **`server/api/scripts/*.py`** (`dedup_catalog`, `reverify_platform_ids`, `resync_catalog_artist`, `backfill_catalog_artists`, `dedup_artists_deezer`, `cleanup_artists`, `backfill_albums`, `import_trackid_index` (C11), `import_beatport_matches` (write path of the local `worker/beatport_backfill/` tool: reads an NDJSON of scraped Beatport matches on stdin, writes via `enrich_from_beatport`+`_mark_searched`), `import_trackid_clean` (write path of the local `worker/trackid_hydrate/` clean-hydration tool: ingests a per-set enrichment BUNDLE NDJSON on stdin and REPLAYS the import/enrichment funnel verbatim — `import_audiostream(prefetched_detail=)` + `bulk_get_or_create_catalog` + Deezer `enrich_entry`/artist+album linkers + `enrich_from_beatport` + BPM `analysis` + embedding insert — resolving identity against the LIVE DB, ZERO network I/O [every value + artwork comes from the bundle bytes, `upload_from_url` suppressed], transactional per set, dry-run/dump-first/idempotent), `backfill_set_search_text` (populate `sets.search_text` for existing rows), `retitle_virtual_parents` (re-title dedup virtual parents with the best child title + refresh their `search_text`), …). The bare `scripts/<x>.py` shorthand used elsewhere in this file ALWAYS means this dir (it ships inside the image under `api/`, so `docker compose exec api python scripts/<x>.py` works). Do NOT confuse it with **`server/scripts/`** — a DIFFERENT dir holding build/ops shell scripts + the schema-doc generator (`backup.sh`, `backup_freshness_check.sh`, `generate_schema_doc.py`, `bootstrap_tidal_tokens.py`), which is EXCLUDED from the build context by `server/.dockerignore` (`scripts/` = `server/scripts/`, not `server/api/scripts/`). These OPS data scripts run a fixed prod sequence: (1) deploy the script first (push → CI → image); (2) **dry-run** `docker compose exec api python scripts/<x>.py` (default = read-only, writes nothing) and read the counters; (3) take an **encrypted dump** (`docs/restore.md`) BEFORE any `--apply`; (4) `--apply`; (5) re-dry-run to confirm convergence (idempotent). NEVER `--apply` without a fresh dump. All these scripts are dry-run-by-default and idempotent.
- Local vs prod: local = `docker-compose.yml` + override (hot reload, port 8080 HTTP); prod = `COMPOSE_FILE` chains `docker-compose.ssl.yml` (ports 80/443, certbot container).
- After deploying, run `/deploy_verify`.
